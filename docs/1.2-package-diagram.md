# 1.2 Package Diagram Redesign

## 1. Problems in Current Package Design

The backend diagram is organized only by technical layer (`controller`, `service`, `repository`, `entity`). A change to one feature therefore spreads across the entire source tree, and every `service.impl` can reach every repository. The arrows also imply DTOs, entities, mappers, controllers, and cross-cutting packages depend on one another in both directions. `JpaRepository` contradicts the actual Mongoose stack.

The frontend diagram has feature packages, but also duplicates auth/security, DTO/mapper, pages/components, API service, and global store responsibilities without rules. This encourages global state and shared DTO packages to become coupling hubs.

## 2. Proposed Package Structure

```text
server/src/
  app.js                         # composition root
  shared/
    kernel/                      # Result, Money, IDs, Clock ports, base errors
    api/                         # HTTP error mapping, request context
    infrastructure/             # logging, config, Mongo connection, event bus
  modules/
    <module>/
      api/http/                  # routes, controller, request schema, presenter
      application/              # use cases, command/query DTOs, application ports
      domain/                    # aggregates, entities, value objects, policies, repo ports
      infrastructure/           # Mongoose schemas/repos, external adapters, jobs

client/src/
  app/                           # router and provider composition
  features/<feature>/
    api/                         # feature API calls and wire DTO mapping
    model/                       # feature state, query hooks, form schemas
    ui/                          # feature-specific components
    pages/                       # route-level feature screens
  components/ui/                # generic design-system components only
  lib/                           # HTTP client and framework adapters
  layouts/                       # role-oriented page shells
```

Backend module names: `identity-access`, `movie-catalog`, `cinema-scheduling`, `booking-ticketing`, `concession-sales`, `promotion`, `payment-refund`, `cinema-operations`, and `reporting-analytics`.

## 3. Responsibility of Each Package

| Package | Responsibility |
| --- | --- |
| `<module>/api/http` | HTTP-only validation, authentication context extraction, controller/presenter logic |
| `<module>/application` | Named use cases, transaction orchestration, command/query models, outbound capability ports |
| `<module>/domain` | Module-owned invariants and model; repository ports live beside the aggregates they persist |
| `<module>/infrastructure` | Mongoose mapping, repository adapters, provider clients, job triggers |
| `shared/kernel` | Small stable primitives with no feature meaning; never a dumping ground |
| `shared/api` | Reusable Express middleware and HTTP error/result mapping |
| `shared/infrastructure` | Configuration, logging, Mongo bootstrap, and technical event dispatch |
| `client/features/<feature>` | A vertical UI slice with its API mapping, state/query model, UI, and route pages |
| `client/components/ui` | Reusable visual primitives with no business workflow |
| `client/lib` | Framework/vendor adapters such as Axios configuration |

## 4. Package Dependency Rules

- Within a backend module: `api -> application -> domain`; `infrastructure -> application/domain`.
- `domain` packages are framework-free and do not import `shared/api` or `shared/infrastructure`.
- One module may depend on another only through the target module's exported application contract or a declared event/read port.
- No module imports another module's Mongoose model, repository implementation, controller, or internal DTO.
- `shared` contains no cinema-specific entity, workflow, or repository.
- Frontend pages compose feature UI; shared UI does not import a feature.
- Feature API modules use the shared HTTP client, but the shared client never imports features.
- Global client state is limited to cross-cutting session/preferences; server state belongs in feature query caches.

## 5. Old to New Package Mapping

| Old package | New package |
| --- | --- |
| `controller` | `modules/<module>/api/http` |
| `service`, `service.impl` | `modules/<module>/application`; invariant logic moves to `domain` |
| `repository` | repository port in `domain`; Mongoose implementation in `infrastructure/persistence` |
| `entity` | aggregate/entity/value object in `domain`; persistence schema in `infrastructure/persistence` |
| global `dto.request/response` | request/response model next to controller or use case |
| global `mapper` | mapping next to the adapter that owns the translation |
| `security`, `exception`, `apiresponse` | `shared/api` middleware/mapping plus Identity & Access policies |
| `enums` | owning domain module; only truly universal primitives in `shared/kernel` |
| frontend `api-services`, `DTO`, `mapper` | each `features/<feature>/api` |
| frontend business `store` | each `features/<feature>/model`; session-only state may remain app-level |
| frontend `security` | router guards plus Identity & Access feature model |

## 6. Design Rationale

Vertical modules localize change and ownership. The inner split preserves separation of concerns without creating one global layer for every technical role. Repository and integration ports reverse infrastructure dependencies and eliminate the false JPA abstraction. The same boundaries appear in the architecture and class diagrams, so diagrams describe implementable packages rather than an unrelated ideal.

Assumption: MongoDB references and embedded documents will be chosen per aggregate boundary, not by mirroring a relational schema.

Open Design Question: decide whether `concession-sales` owns online concession orders independently or whether every concession purchase is part of a common `Sale/Order` aggregate shared with booking. The diagrams keep a separate `ConcessionOrder` while reusing payment ports.
