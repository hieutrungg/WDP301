# 1.1 Software Architecture Redesign

## 1. Problems in Current Design

The SDS describes the same backend as Spring Boot, Express, JPA, MySQL, MongoDB, and a generic "3-tier" system. The repository, however, is a React 19 client and an Express 5/Mongoose backend. This contradiction makes the architecture diagram, package diagram, sequence diagrams, and class diagrams describe different systems.

The current application box also collapses HTTP handling, authorization, workflows, business rules, persistence, scheduled jobs, and external integrations into one layer. Most class diagrams repeat `Controller -> ServiceImpl -> many repositories`, so business rules have no explicit owner and use cases become highly coupled transaction scripts. Repository interfaces inherit from `JpaRepository` even though the documented and implemented database is MongoDB. Frontend packages are partly technical and partly feature-oriented, with dependencies left unspecified.

Cross-cutting concerns are also modeled as ordinary dependencies. Security, validation, error mapping, logging, jobs, and notifications should surround use cases or implement ports; domain objects should not depend on them. The existing diagrams do not show transaction/concurrency boundaries for seat holds, voucher redemption, payment callbacks, refunds, or inventory updates.

## 2. Proposed Architecture

Use a **modular monolith with Clean/Hexagonal Architecture inside each business module**. This matches the current deployment shape while creating boundaries that can later be extracted if scale requires it.

- **React SPA**: feature-oriented UI, routing, state/query adapters, and an HTTP client.
- **HTTP/API adapters**: Express routes, controllers, request validation, authentication middleware, authorization policies, and response/error mapping.
- **Application layer**: explicit use-case services, commands/queries, DTOs, transaction orchestration, and domain-port calls.
- **Domain layer**: aggregates, entities, value objects, invariants, policies, and repository/integration port interfaces.
- **Infrastructure adapters**: Mongoose persistence, payment and notification clients, report exporters, job runners, clock/ID implementations, logging, and observability.
- **MongoDB**: authoritative persistence store, with atomic updates/transactions where an invariant spans documents.
- **External systems**: payment gateway and email/SMS provider, accessed only through outbound ports.

The logical modules are Identity & Access, Movie Catalog, Cinema Scheduling, Booking & Ticketing, Concession Sales, Promotion, Payment & Refund, Cinema Operations, and Reporting & Analytics. Cross-module calls go through application interfaces or stable read ports; modules never import another module's Mongoose model or repository implementation.

## 3. Responsibility of Each Layer and Component

| Layer or component | Responsibility |
| --- | --- |
| React feature UI | Render workflows, collect input, hold ephemeral UI state, call backend APIs, and display results. It does not decide business eligibility. |
| Express API adapters | Translate HTTP into commands/queries, validate syntax, authenticate/authorize, invoke one use case, and map results/errors to HTTP. |
| Application services | Coordinate one business use case, define consistency boundaries, call domain behavior and ports, and publish events after successful changes. |
| Domain model | Enforce business invariants such as seat-hold lifecycle, booking transitions, voucher eligibility, ticket check-in, refund rules, and stock movement. |
| Domain/application ports | Define capabilities required from persistence and external services without exposing Mongoose or vendor SDK types. |
| Infrastructure adapters | Implement ports using Mongoose, payment/notification SDKs, background jobs, file exporters, and other technical mechanisms. |
| Composition root | Wire controllers, use cases, repositories, adapters, middleware, configuration, and job runners. |
| MongoDB | Persist module-owned documents and support indexed/atomic operations. It is not called directly from controllers or domain objects. |
| Payment gateway | Create/verify payment transactions and execute refunds through `PaymentGatewayPort`. |
| Notification provider | Deliver OTP, booking, ticket, and refund notifications through `NotificationPort`. |

## 4. Dependency Rules

1. `api -> application -> domain` is the only inward compile-time direction.
2. `infrastructure -> application/domain` because adapters implement inward-owned ports.
3. Domain code imports no Express, Mongoose, React, vendor SDK, or environment/config module.
4. Controllers invoke use-case interfaces and never repositories or Mongoose models.
5. Repository interfaces use domain terminology; Mongoose schemas and query details remain in infrastructure.
6. Modules do not import other modules' infrastructure. A module may call another module through an application API, a read port, or a published domain event.
7. Shared code is restricted to stable primitives and technical middleware; business concepts stay in their owning module.
8. Scheduled jobs invoke the same application use cases as HTTP adapters and must be idempotent.
9. Payment callbacks, ticket scans, voucher redemption, seat acquisition, and stock changes require idempotency or atomic compare-and-set semantics.
10. Reporting reads may use dedicated projections, but reporting must not mutate operational aggregates.

## 5. Design Rationale

The modular monolith avoids distributed-system complexity while the product and team are still evolving. Clean boundaries isolate the business rules that are currently scattered across large services. Ports make payment, notification, persistence, clock, and export mechanisms replaceable and testable. Feature ownership matches the repository's existing `server/src/modules` and `client/src/features` direction, so migration can be incremental rather than a rewrite.

MongoDB is retained because both the database-design section and implementation use it. Mongoose-specific concerns are kept outside the domain so the model does not pretend to be JPA. The design distinguishes write aggregates from reporting projections, preventing analytics queries from inflating operational services.

## 6. Mapping From Old Design to New Design

| Current concept | New location or treatment |
| --- | --- |
| ReactJS presentation layer | `client/src/features`, `pages`, `layouts`, and shared UI/lib packages |
| Controller layer | Per-module `api/http` adapters |
| Service / ServiceImpl | Named application use cases; reusable business rules move to domain policies/services |
| Entity | Domain aggregate/entity/value object; Mongoose document mapping moves to infrastructure |
| Repository extending JPA | Domain-owned repository port plus Mongoose adapter |
| DTO/request/response | Per-use-case API/application DTOs; not shared globally |
| Mapper | Adapter-bound mapping next to HTTP or persistence code |
| Security | HTTP authentication middleware plus application authorization policy/port |
| Scheduler classes | Infrastructure job adapters invoking idempotent application use cases |
| PaymentGatewayClient | Infrastructure adapter implementing `PaymentGatewayPort` |
| Email/SMS service | Infrastructure adapter implementing `NotificationPort` |
| Report entity/repository | Read projections and exporter ports; persist a report artifact only if a requirement demands it |

## 7. Diagram Explanation

The diagram shows runtime communication with solid arrows and compile-time dependency direction with labeled inward arrows. The domain core is at the center. Application use cases depend on the core and its ports; API and infrastructure sit outside. MongoDB and external providers are reached only through adapters. Module boundaries cut vertically through the application/domain layers, while shared technical facilities remain outside business modules.

Assumption: the target implementation remains a single Express process and a single MongoDB deployment.

Open Design Question: the SDS mentions both JWT/token handling and server-side session invalidation. The team must choose the authentication/session strategy before finalizing logout and token-revocation design.
